# xLights and Tesla interoperability

Reviewed 2026-09-27. LightForge uses Tesla's xLights channel layout and command
protocol as its sequencing contract. Its music analysis, cue planning, vehicle
simulation and FSEQ writer remain independently implemented.

## Upstream basis

| Source | Pinned revision | Use |
| --- | --- | --- |
| [Tesla light-show](https://github.com/teslamotors/light-show/tree/9f949512146d881b6eb66d042b22ee3f9e115afb) | `9f949512146d881b6eb66d042b22ee3f9e115afb` | Channel addresses, commands, FSEQ compatibility and official validator |
| [xLights](https://github.com/xLightsSequencer/xLights/tree/a1a20e4facd5113c5afc5768ac3cb0b43acd81d5) | `a1a20e4facd5113c5afc5768ac3cb0b43acd81d5` | FSEQ reader/writer architecture and independent readback |

Tesla's currently published README, validator and template match the reference
files already retained in `research/hardware-1.2.0`. The new interoperability
test pins the validator and XML hashes and compares **every** vehicle-profile
output with named models in that official XML, including coupled headlamp
channels and RGB triplets. A change of address or missing audit row fails.

The Tesla template is a superset across vehicles. It is an address reference,
not a Highland body model. The app's profile omits unsupported closures and
unfitted lamps. Model 3 channel 4/5/6 coupling, shared park/marker output,
command-driven ramps and closure behavior remain part of the physical-output
simulation. This does not establish undocumented headlamp sub-lens routing.

## Integration decision

xLights separates effects, channel buffers and FSEQ persistence. Its
`src-core/render/SequenceData.h`, `src-core/effects/OnEffect.cpp` and
`src-core/render/FSEQFile.cpp` informed this review. LightForge's corresponding
boundary is musical targets → physical-output scheduling → command frames →
FSEQ. The preview reads the same command frames used by export.

The [xLights license](https://github.com/xLightsSequencer/xLights/blob/a1a20e4facd5113c5afc5768ac3cb0b43acd81d5/License.txt)
is GPL version 3. Incorporating its implementation would introduce distribution
and source-license obligations requiring a deliberate licensing decision for
this project and its model assets. No xLights implementation or desktop runtime
is bundled in the Android app. Instead, its unmodified FSEQ reader is used as an
external development-time interoperability oracle. This also avoids adding its
desktop rendering stack to an offline Android music-analysis workload.

This work does not claim importing xLights would accelerate the app's neural
inference. The reader check measures compatibility, not a performance gain.

## Verified contract and correction

The release regression gate now:

- Parses Tesla's official xLights layout and checks all profile output addresses.
- Runs 15 ms and 20 ms production FSEQ exports through Tesla's official Python
  validator, then independently checks the 200-channel payload, version,
  metadata bounds and uncompressed layout. Tesla's validator by itself is a
  format check; it does not validate vehicle choreography or physical timing.
- Checks raw frame access and physical preview against the same frame boundary
  across 17,498 timestamps. Previously, floating-point conversion could select
  the preceding raw frame, for example at 4.02 seconds with a 20 ms interval.
  Both APIs now share a bounded floating-point tolerance. Earlier timestamps
  remain in the preceding frame; non-finite values consistently select time zero.

An additional external check compiled the pinned xLights `FSEQFile.cpp` and
`FSEQFile.h`, using `-std=c++17 -O2 -DNO_ZSTD` and `-lz`. The independent harness
in `research/xlights-contract-2026-09-27/reader.cpp` calls upstream
`openFSEQFile`, `prepareRead` and `getFrame` for every frame. Neither the xLights
sources nor the resulting executable are redistributed with the app.

For the existing `tests/engine-glass-castle.json` feature fixture, the upstream
reader returned the exact generated bytes at both app frame intervals:

| Interval | Frames | Payload bytes | Result |
| --- | ---: | ---: | --- |
| 15 ms | 15,870 | 3,174,000 | All bytes equal |
| 20 ms | 11,902 | 2,380,400 | All bytes equal |

Source, fixture, exported-file and payload hashes are recorded in
`research/xlights-contract-2026-09-27/verification.json`. These are bounded
development-fixture observations, not a signed APK qualification or physical
vehicle test. Re-running this optional external check requires obtaining the
pinned upstream source and its license; normal regression tests use the pinned
Tesla fixtures already in the repository and add no production dependencies.

## Accuracy boundary

Command frames have a defined digital clock. Audible playback, vehicle light
response, motors, firmware, temperature and the installed lamps add physical
behavior that FSEQ and a VIN cannot measure. Preview motion remains an estimate
unless calibrated against the actual vehicle. No compatibility result here
establishes exact per-lens optical appearance or real-car synchronization.
